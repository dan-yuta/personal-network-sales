## 既存「営業候補リスト」DB のスキーマ詳細

### プロパティ一覧

| プロパティ名 | 型 | 説明 | UI上の扱い |
|------------|----|----|-----------|
| 顧客企業名 | Title | 個人事業主は屋号、なければ「個人」 | Pane2/Pane3 表示・読み取りのみ |
| 顧客名 | Text | 個人名（イニシャル可） | Pane2/Pane3 表示・読み取りのみ |
| 進捗状況 | Select | 営業ステータス | Pane1ステージ・Pane3編集可 |
| 優先度 | Select | 高 / 中 / 低 | Pane2/Pane3表示・編集可 |
| 担当者 | Person | Notionユーザー | Pane3表示のみ |
| Email | Email | メールアドレス | Pane3表示・mailto:リンク |
| 連絡先 | Text | LINE ID・SNSアカウント名 等 | Pane3表示のみ |
| 郵便番号 | Text | 郵便番号 | Pane3表示のみ |
| 住所 | Text | 住所 | Pane3表示のみ |
| リンク | URL | HP・SNSプロフィール | Pane3表示・外部リンク |
| 名刺 | File | 名刺画像 | Pane3サムネイル表示 |
| 備考 | Text | 業種・背景・意思決定肩書他 | Pane3表示のみ |
| 進捗詳細 | Text | 自由メモ | Pane3表示・編集可（自由メモ領域） |
| 次回アクション | Text | 次にやること | Pane3編集可・Pane4フォームでも上書き |
| 次回アクション期限 | Date | 期限日 | Pane3編集可・Pane2並び替えキー |
| 最終連絡日 | Date | 連絡間隔警告に使用 | **自動更新（ログDB追加時）** |
| バック人脈 | Text | 紹介者・後ろ盾 | Pane3表示のみ |
| 親レコード | Relation (自己) | 紹介元レコード | Pane3でリンク表示 |
| 間柄 | Relation→間柄DB | どのコミュニティ経由か | Pane3でリンク表示 |

## 新規「接触ログ」DB のスキーマ

### プロパティ一覧

| プロパティ名 | 型 | 説明 | 必須 | デフォルト値 |
|------------|----|----|------|-------------|
| 件名 | Title | "{日付} {手段}" の自動生成 | ○ | 自動 |
| 日付 | Date | 接触した日 | ○ | 今日 |
| 手段 | Select | 接触手段 | ○ | （選ぶ） |
| 内容 | Text | 何を話したか | ─ | 空 |
| 候補者 | Relation → 営業候補リスト | どの候補者への接触か | ○ | （Pane3 で選択中の候補者） |

### 手段の選択肢

```
  ┌────────┬────────┬──────┬──────┬──────────────┬─────┬────────┐
  │ 電話   │ メール │ LINE │ 訪問 │ ｵﾝﾗｲﾝ会議    │ SNS │ その他 │
  └────────┴────────┴──────┴──────┴──────────────┴─────┴────────┘
```

### Notion 上での配置

```
営業候補管理ページ
  ├─ 📊 営業候補リスト (既存)
  └─ 📊 接触ログ      (新規追加)  ◄── ここに作成
```

両DBが同じ親ページ配下にあれば、Notion 上での運用も一覧性が保たれます。

## 同期規約（Notion ⇔ UI）

接触ログの追加・編集を Notion に書き戻すとき、関連する既存レコードをどう更新するかを明確に定めます。

### ルール表

| トリガー | 更新先 | 更新内容 |
|---------|--------|----------|
| 接触ログ新規追加（タブA） | 接触ログDB | 新規ページ作成（日付・手段・内容・候補者リレーション） |
| 接触ログ新規追加（タブA） | 営業候補リストDB | 「最終連絡日」を新ログの日付で**自動上書き** |
| 接触ログ追加フォームで「次回アクション」を入力（タブA） | 営業候補リストDB | 「次回アクション」「次回期限」を**手動上書き**（フォーム送信時） |
| 接触ログ削除・修正 | 営業候補リストDB | 「最終連絡日」を**最新ログから再計算**して更新 |
| Pane3 で「進捗状況」「優先度」を変更 | 営業候補リストDB | 該当プロパティのみ更新 |
| Pane3 で「進捗詳細」を編集 | 営業候補リストDB | 「進捗詳細」のみ更新（自由メモ領域、自動でログから合成しない） |
| **連絡文タブB で「接触ログとして保存」** | 接触ログDB | 新規ページ作成（日付=今日・手段=生成媒体・内容=生成文の要約 or 本文）。タブA経由と同様、営業候補リストの「最終連絡日」も自動更新 |

### 「最終連絡日」自動同期のフロー

```
   ユーザー: 接触ログを追加
       │
       ▼
   ┌─────────────────────────────────┐
   │  Step 1: 接触ログDB に新規ページ │
   │           作成 (POST)            │
   └─────────────────────────────────┘
       │
       ▼
   ┌─────────────────────────────────┐
   │  Step 2: 候補者の最新ログ日付を  │
   │           算出 (今追加分含む)     │
   └─────────────────────────────────┘
       │
       ▼
   ┌─────────────────────────────────┐
   │  Step 3: 営業候補リストDB の     │
   │           「最終連絡日」を更新    │
   │           (PATCH)                │
   └─────────────────────────────────┘
       │
       ▼
   ┌─────────────────────────────────┐
   │  Step 4: もしフォームで「次回    │
   │           アクション」も入力済み │
   │           なら、それも同時に更新 │
   └─────────────────────────────────┘
       │
       ▼
     完了
```

## 設計判断の根拠

### なぜ「会社」と「担当者」を分離しないか

```
   案A: フラット構造 (採用)        案B: 階層構造 (不採用)
   ─────────────────────           ─────────────────────
                                   ┌──────────┐
   ┌──────────────┐                │  会社DB  │
   │ 営業候補リスト│                └────┬─────┘
   │ 1人=1ﾚｺｰﾄﾞ   │                     │ 1:N
   └──────────────┘                     ▼
                                   ┌──────────┐
   ・既存DB流用OK                  │ 担当者DB │
   ・現状の顧客規模(数十)で十分    └──────────┘
   ・Notion運用変更ゼロ            
                                   ・既存データ移行が必要
                                   ・規模が倍以上にならないと
                                     恩恵が出ない
                                   ・運用が複雑化
```

採用理由:
- 既存DBは1人=1レコードの構造で運用済み（変更コスト大）
- 同時進行案件は数十件規模で、階層化のメリットが出ない
- B2B営業で「同一会社に複数担当者」のケースは発生するが、現状は「顧客企業名」テキストで十分管理できる

### なぜ「接触ログDB」だけ追加するか

```
   ┌──────────────────────────────────────┐
   │  営業ツールの「生命線」=接触ログ      │
   │                                      │
   │   いつ・どの手段・何を話したか        │
   │   を時系列で振り返れること           │
   └──────────────────────────────────────┘
                    │
                    │ 既存DBで実現可能か?
                    ▼
        ┌──────────────────────────────┐
        │ 「進捗詳細」テキスト1個では   │
        │  最後の1件しか保存できない    │
        │  履歴を追えない               │
        └──────────────────────────────┘
                    │
                    ▼
            別DBで時系列管理が必須
                    │
                    ▼
              接触ログDB を追加
```

### なぜ「進捗詳細」テキストには手をつけないか

- ユーザーが既に自由メモ領域として使っている
- 接触ログDBが「構造化されたログ」を担うなら、自由メモは別役割として残す方が運用が柔軟
- 二重保存にしてしまうと、Notion を直接見たとき情報が冗長になる

## データボリューム見積もり

| データ | 月間追加数 | 年間累積 | 5年累積 |
|--------|-----------|---------|---------|
| 営業候補（人） | +20〜30 | 240〜360 | 1,200〜1,800 |
| 接触ログ | +60〜100（1日2〜3件×営業日20日） | 720〜1,200 | 3,600〜6,000 |

→ いずれも Notion DB の実用範囲（〜数万件）に余裕で収まります。
