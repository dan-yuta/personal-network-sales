# 03. データ設計書

> **【2026-06-09 更新】** 本書は5月時点の想定をベースに、第7回宿題（Notion 永続化＋Vercel 公開）の実装に合わせて現状化した（**実装の正は [notes/2026-06-08_session-record.md](../notes/2026-06-08_session-record.md)**）:
> - 進捗状況は **7段階**（アプローチ中と商談中の間に「紹介進行中」を追加）。
> - 接続は **@notionhq/client v5 のデータソースAPI**（`databases.query` は廃止 → `dataSources.query` を使用。ページ作成の親は `data_source_id`）。環境変数の各 ID は **データソースID** を入れる。
> - DB は **2セット運用**（公開=デモ/ダミー `3764fafd…`＋接触ログ `07c04273…`、ローカル=本番 `b36fdbb0…`）。`env` 切替で同じコードがどちらにも向く。
> - 永続化は実装済み: **ステージ／プロフィール／評価4軸／アーカイブ／接触ログ追加／最終連絡日同期**。`listCandidates()` で Notion 取得（`page.tsx` は `force-dynamic` で毎リクエスト最新）、編集は Server Action（`app/actions.ts`）で `pages.update`。
> - 評価4軸は候補者DBの **数値列（現在スナップショットのみ・履歴なし）**。`接触経路` text 列を追加（source 用）。
> - 担当者(person)・リンク(url) は今回スコープ外（**読み取りのみ・書かない**）。間柄/親レコード(relation)・名刺(file) は**未読取**、郵便番号(text) は**未取込**（読み取りも UI 表示もしておらず、スキーマ枠のみ／枠すら無し）。
> - データ層は `tool/lib/notion/{client,props,schema,candidates,contact-logs}.ts`。Notion 生プロパティ → `parseCandidatePage()`/`parseLogPage()` で正規化（`zod`、欠損列は null/false/[] 許容＝本番DB/デモDBの差異両対応）→ `toCandidate()` で UI 用 `Candidate`（`tool/lib/schema.ts`）へ変換。

> **補足: Notion ⇔ UI のデータ同期戦略（実装済み）**
>
> Notion を SSoT とし、以下の流れで永続化している（詳細は `tool/app/actions.ts` / `tool/lib/notion/*`）:
>
> - **読取**: `page.tsx` は `export const dynamic = "force-dynamic"` で毎リクエスト最新化し、`listCandidates()` が `dataSources.query` をページネーション取得 → `toCandidate()` で UI 配列へ。`NOTION_TOKEN` 未設定時のみ `tool/data/candidates.json` のシードへフォールバック（編集は永続化されない）。
> - **編集**: クライアント（`Workspace` 配下）は楽観的更新で即時反映し、Server Action（`updateStageAction` / `updateProfileAction` / `updateAxisScoresAction` / `setArchivedAction` / `listContactLogsAction` / `addContactLogAction` の 6 個。`listContactLogsAction` は接触ログ取得＝読取専用）が `pages.update`（または接触ログは `pages.create`、取得は `dataSources.query`）で書き込む。各 action は `revalidatePath("/")` で Server Component の再フェッチをトリガ。失敗時は例外が伝播し、クライアントでロールバック＋トースト（テキスト欄は uncontrolled のため巻き戻し不可＝通知のみ、リロードで最新に揃う）。全書込は直列キュー（`writeChainRef`）に通して連打・順序逆転・レート制限を回避。
> - **最終連絡日**: 接触ログ追加時に候補者レコードの「最終連絡日」を新ログ日付で `pages.update` 同期（denormalized）。UI バッジは `Candidate.lastContactDate` を参照。
> - **件数バッジ** (Pane1 ステージタブの「未連絡 3」等): `Workspace` の `stageCountMap` で（Notion 由来の）candidates 配列から `useMemo` 派生。
> - **平均スコア** (★ X.X): `getCandidateAverageScore(candidate)` で評価4軸スナップショットの平均を派生計算。

## 設計判断の根拠

### なぜ「会社」と「担当者」を分離しないか

```
   案A: フラット構造 (採用)        案B: 階層構造 (不採用)
   ─────────────────────           ─────────────────────
                                   ┌──────────┐
   ┌──────────────┐                │  会社DB  │
   │ 営業候補リスト│                └────┬─────┘
   │ 1人=1ﾚｺｰﾄﾞ   │                     │ 1:N
   └──────────────┘                     ▼
                                   ┌──────────┐
   ・既存DB流用OK                  │ 担当者DB │
   ・現状の顧客規模(数十)で十分    └──────────┘
   ・Notion運用変更ゼロ            
                                   ・既存データ移行が必要
                                   ・規模が倍以上にならないと
                                     恩恵が出ない
                                   ・運用が複雑化
```

採用理由:
- 既存DBは1人=1レコードの構造で運用済み（変更コスト大）
- 同時進行案件は数十件規模で、階層化のメリットが出ない
- B2B営業で「同一会社に複数担当者」のケースは発生するが、現状は「顧客企業名」テキストで十分管理できる

```
                    │

                    ▼
        ┌──────────────────────────────┐
        │ 「進捗詳細」テキスト1個では   │
        │  最後の1件しか保存できない    │
        │  履歴を追えない               │
        └──────────────────────────────┘
                    │
                    ▼
            別DBで時系列管理が必須
                    │
                    ▼
              接触ログDB を追加
```

### なぜ「進捗詳細」テキストには手をつけないか

- ユーザーが既に自由メモ領域として使っている
- 接触ログDBが「構造化されたログ」を担うなら、自由メモは別役割として残す方が運用が柔軟
- 二重保存にしてしまうと、Notion を直接見たとき情報が冗長になる

## データボリューム見積もり

| データ | 月間追加数 | 年間累積 | 5年累積 |
|--------|-----------|---------|---------|
| 営業候補（人） | +20〜30 | 240〜360 | 1,200〜1,800 |
| 接触ログ | +60〜100（1日2〜3件×営業日20日） | 720〜1,200 | 3,600〜6,000 |

→ いずれも Notion DB の実用範囲（〜数万件）に余裕で収まります。
