## 1. 設計優先 — `grill-me` で1問ずつ詰めた

### 何をしたか

`/grill-me` スキルを使って、計画段階で発生する全ての分岐を AI に1問ずつ質問してもらい、合意できた決定だけを設計に書き残しました。

```
   ツールの目的 → 業務テーマ → スコープ → UI骨格
        │            │           │         │
        ▼            ▼           ▼         ▼
    人脈営業    リード〜受注    ステージ   4ペイン
              　 　　完了      　4段階    踏襲
```

### 効果

- 「**なんとなく作り始めて行き詰まる**」を回避
- 分岐ごとに **「なぜその判断にしたか」が docs に残る**
- 後から仕様変更が出ても、判断ログを辿って影響範囲を見られる

### 具体例

「会社単位 vs 担当者単位」の選択。grill-me で「既存 Notion DB は 1人=1レコード構造」と判明し、「**既存構造を尊重して階層化はしない**」と早期決定できた。

## 2. 既存 Notion DB を尊重 — ゼロから作らない

### 何をしたか

既存の Notion DB「営業候補リスト」をそのまま流用し、UI 側のスキーマをそれに合わせる方針を採用しました。

```
   ❌ よくある失敗:  「理想のスキーマ」を新規DBで構築 → 既存データの移行コスト大
   ✅ 採用した判断:  既存DBの19プロパティをそのまま使い、UI側を合わせる
```

### 効果

- データ移行ゼロ
- 既存の Notion ワークフロー（検索・フィルタ・テンプレート）を壊さない
- 将来 UI を捨てても Notion 側にデータが残る

### 設計判断のログ

`03_データ設計書.md` に詳述。

## 3. 接触ログ DB だけ追加 — スキーマ拡張は最小限に

### 何をしたか

「ツールの生命線である接触ログ」だけを新規 DB として追加し、それ以外（会社 DB・担当者 DB の分離）は **見送り**ました。

```
   営業候補リスト (既存・19プロパティ・流用)
        │ 1:N
        ▼
   接触ログ (新規・4プロパティだけ)
   - 日付
   - 手段 (電話/メール/LINE/訪問/オンライン会議/SNS/その他)
   - 内容
   - 候補者 (relation)
```

### 効果

- Notion 側の DB が **2つだけ**で済む
- 「会社×担当者×案件」のような階層化は、規模が増えてからでも遅くない
- 「過剰設計しない」を意識した設計

## 4. Pane1 をステージタブに転用 — テンプレートの階層を活かす

### 何をしたか

`workspace-ui-kit` テンプレートの Pane1 (部署/ポジション階層) を、**営業ステージのタブ表示**に転用しました。

```
   元: 部署 > ポジション
      プロダクト開発 > フロントエンドエンジニア
   新: メインステージ > 個別ステージ
      メインステージ > 未連絡 / アプローチ中 / 商談中 / 契約
      サブステージ   > 失注 / 保留
```

### 効果

- テンプレートの SidebarMenu 構造をそのまま流用 → コード変更最小
- ステージクリックで Pane2 を絞り込む動線を追加（`selectedStage` state）

## 5. Pane4 をタブ化 — 接触ログと連絡文作成を同居

### 何をしたか

`workspace-ui-kit` のテンプレートでは Pane4 が「選考ステージ詳細編集」専用でしたが、これを **タブ化** して「接触ログ」と「連絡文作成」を切り替えられる構造にしました。

```
   [● 接触ログ]  [○ 連絡文作成]
   ────────────────────────────
     (タブで切り替え)
```

### 効果

- Pane4 という「次の一手を推す部屋」に2機能を同居できる
- 横スクロールや別画面遷移なしで、両方アクセス可能
- 認知負荷も Pane サイズも軽く保てる

### 設計の出典

`02_UI設計書.md` の Pane4 タブ化議論。

## 6. 連絡文に Vision 対応 — スクリーンショットも入力可能（設計のみ・実装は Phase E）

> この項目は **UI と設計方針** の工夫です。AI による連絡文生成そのものは発展課題（Phase E）として**未実装**で、連絡文作成タブは現状サンプル文を返します（#9 参照）。

### 何をしたか

連絡文作成タブで、**過去のやり取りを「文面コピー」と「スクリーンショット画像添付」の両方で AI に渡せる**設計にしました。

```
   入力: シーン + 媒体 + 補足 + 過去のやり取り (文面 or 画像)
                                          ↓
                          Claude Sonnet 4.6 (vision 対応)
                                          ↓
                              生成された下書き文
```

### 効果

- メール文面 → テキストコピーが早い
- LINE のやり取り → スクリーンショットの方が早い
- ユーザーが場面で使い分けられる
- AI に「先方の温度感・話題・口調」を読み取らせて反映

## 7. テンプレート参照と実装の分離 — 書き換え禁止フォルダを設ける

### 何をしたか

`workspace-ui-kit` の原本は **絶対に書き換えない** ルールで OneDrive 配下 `100_tool/workspace-ui-kit/` に保管し、実装は `personal-network-sales/tool/` にコピー（`robocopy` という Windows のフォルダ複製コマンドを使用）したものを書き換える方針を採用。

> 2026-05-24 のセッションでリポジトリ全体を OneDrive 外 (`C:\Users\dangi\src\personal-network-sales\`) に移行済み。`tool/` の正本もこのパス。

```
   100_tool/workspace-ui-kit/          ← テンプレート (書き換え禁止)
                │ robocopy
                ▼
   personal-network-sales/tool/        ← 実装モジュール (編集対象)
```

### 効果

- いつでも「元のテンプレート」と比較できる
- 「テンプレートのどこを変えたか」が `git diff` で明示できる
- 将来 workspace-ui-kit がアップデートされても、原本に上書きできる

## 8. 採用→営業 語彙の一括置換 — zod key は維持

### 何をしたか

テンプレートの **採用管理ドメインの語彙**（書類選考・面接官・希望年収・応募経路・選考フロー…）を、営業ドメインの語彙（未連絡・担当者・想定取引規模・接触経路・接触ログ…）に一括置換しました。

ただし、`lib/schema.ts` の **zod スキーマの key 自体は維持** （`screening` / `first` / `second` / `final` / `recruiter` 等）。

### 効果

- 表示ラベルだけ差し替えるので、ロジック変更は最小限
- 既存のテスト・派生計算・ヘルパーがそのまま動く
- 後で本格的に rename したくなったら別途対応可能

### 置換の詳細

`02_UI設計書.md` の「実装メモ: 採用語彙→営業語彙の置換実績」セクション参照。

## 9. モック先行 — API 接続前から動く状態を維持（当時）

### 何をしたか

接触ログ・連絡文作成タブを **API 接続なしのモック実装** で先に動くようにしました（5回目セッション時点の工夫）。

```
   接触ログ: 候補者ごとの固定サンプルログを表示 (実 API 接続なし)
   連絡文作成: 媒体ごとに異なる「サンプル文」を JS 内で生成
```

### 効果

- Notion / Anthropic API のセットアップが終わる前から、UI 全体の動作感を確認できる
- グループセッションでの「ここまで作りました」のデモも、API なしで完結
- 後で本物の API に切り替えるとき、UI 側を再設計しなくて良い

### その後（現状）

- **接触ログ・ステージ・プロフィール・評価4軸・アーカイブは Phase C/D で Notion 連携に差し替え済み**（#11〜⑫）。モックは「UI を固めるための設計の踏み台」として役目を終えた。
- `lib/data/mockLogs.ts` はアプリ本体からは未使用化（テストにのみ残置）。
- **連絡文生成だけは今もサンプル文のまま**（実 AI 呼び出しは発展課題 Phase E・未実装）。「先にモックで動かす」判断が、後で本物へ差し替えやすい構造を残せたことの実例になっている。

## 10. 設計と実装の同期コミット — docs と tool/ を同じ PR で

### 何をしたか

設計を変更したら **同じコミットで** docs/ と tool/ の両方を更新する運用を徹底。git で「設計と実装のドリフト」を防ぐ。

### コミット履歴の例

```
b481492 refactor: 未使用コードのクリーンアップ
81a0d65 docs: add submission/tool-overview.html (課題図解)
be16e76 feat: import tool/ (workspace-ui-kit ベース + 営業向けカスタマイズ + Pane改造)
14cf565 docs: add design documents (grill-me 結果反映)
3534045 chore: initial repository setup
```

### 効果

- 「docs では Pane4 タブ化なのにコードは旧 Pane4」のような乖離が起きない
- レビュー時も設計と実装のセットで見られる

## 11. 保存先のハイブリッド設計 — 編集データは Notion / 定義は リポジトリ

### 何をしたか

「何をどこに置くか」を、データの性質で線引きしました。

```
   編集データ (ユーザーが触る実データ)         → Notion
     候補者プロフィール / 評価4軸 / ステージ /
     アーカイブ / 接触ログ / 最終連絡日

   定義・マスタ (アプリの骨格)                  → リポジトリ
     ステージ定義・色・ラベル / 連絡文シーン /
     アプリ設定
```

### 効果

- 人が直接 Notion でデータを見れる・既存の営業ワークフローに乗せられる
- アプリを捨ててもデータは Notion 側に残る
- マスタ定義はコード（＝AI が読める場所）に残るので、改修時に AI が文脈を掴みやすい

### Notion 採用の代償を意識した

推奨候補だった Neon（SQL DB）ではなく Notion を選んだのは、既存業務が Notion 上にあり流用できるため。一方で「**AI との距離が遠くなる**」という代償（講義の論点）も認識し、だからこそ**定義・マスタはリポジトリに残す**線引きにしました。

> 詳細は `../notes/2026-06-08_session-record.md` の「保存先マップ」を参照。

## 12. 楽観的更新＋失敗ロールバック＋書込直列化 — 連打・順序・レート制限に強くする

### 何をしたか

Notion への書き込みを伴う全操作で、UI の即応性と整合性を両立させる仕組みを入れました。

```
   操作 → 画面を即更新 (楽観的更新)
        → Notion へ書込 (writeChainRef のキューで直列実行)
        → 失敗したら画面を元に戻す (ロールバック) + Toast
```

### 効果

- ステージ移動・プロフィール編集・評価4軸・アーカイブ/復元・接触ログ追加すべてに適用
- **書込を直列化**することで、連打・順序逆転・Notion 側レート制限を回避
- **Undo も Notion に反映**（UI だけ戻すとリロードで復活してしまうため）
- 失敗時は画面を巻き戻して「保存できていないのに成功に見える」を防止
  （※テキスト欄など uncontrolled な箇所は巻き戻し不可のため通知のみ・リロードで最新に揃う）

## 13. 公開はダミーDBに向ける — 個人情報漏洩ゼロ

### 何をしたか

Notion DB を **2セット**用意し、環境変数のデータソースIDで切り替える設計にしました。

```
   公開 (Vercel)   → デモDB (30人のダミーデータ・無認証で晒してよい)
   ローカル        → 本番DB (実データ)
```

### 効果

- 公開 URL には**実在の営業先が一切載らない** → 個人情報漏洩リスクをゼロにできる
- `seed-notion.mjs`（冪等シード・本番DB誤爆ガード付き）でデモDBをダミーで満たす
- 公開アプリは無認証・`force-dynamic` で、別端末からでも最新のデモデータを表示

## 14. 真因特定 — 「症状」でなく「原因」を実証してから直す

### 何をしたか

Vercel デプロイが連続失敗（`ENOENT ... routes-manifest-deterministic.json`）した際、目についた症状に飛びつかず、**原因を実証してから**修正しました。

```
   ① bundler を webpack に変更       → 変化なし (red herring)
   ② env / Root Directory 見直し     → 変化なし
   ③ 当該ファイル名を Next.js 本体の
      tarball 複数版で grep          → どの版にも存在しないと実証
        ＝ Next 由来でなく Vercel のデプロイアダプタが扱う成果物と判明
   ④ 真因 = next.config の
      outputFileTracingRoot          → 削除して解決
```

### 効果

- 「ローカル成功・Vercel のみ失敗」という症状が、アダプタはローカルで走らない事実と一致 → 仮説の裏が取れた
- 当てずっぽうの試行錯誤でなく、**そのファイルが Next 本体に存在しないことを tarball の grep で実証**してから真因に到達
- 修正は一点（`outputFileTracingRoot` 削除・コミット `2950b8b`）で済んだ
