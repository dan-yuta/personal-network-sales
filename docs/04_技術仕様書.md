### 失敗時のロールバック設計

| 失敗パターン | 対応 |
|------------|------|
| Notion API がタイムアウト | 5秒待ってリトライ1回、失敗ならロールバック |
| 認証失敗 (401/403) | トースト + 入力値を保持 + 環境変数チェックを促す |
| バリデーション失敗 (400) | 楽観的更新前にクライアント側zodでブロック（API呼ばない） |
| ネットワーク断 (offline) | トースト「オフラインです」+ 入力値保持 |

## 連絡文作成機能の技術構成（発展課題 Phase E・実装完了）

> 実装完了。`lib/anthropic/draft-message.ts` の `generateDraftMessage`（候補者基本＋
> 接触ログ直近3件＋過去画像を組み立て、system に prompt caching、`max_tokens` 1024、
> モデルは `ANTHROPIC_MODEL` で出し分け）→ `app/actions.ts` の `draftMessageAction`
> （"use server"）→ タブB `DraftMessageTab`（シーン11×媒体3＋補足＋画像最大3枚＋
> 微調整＋接触ログ保存）まで配線済み。
>
> **公開ポリシー（確定）**: AI 生成は `ANTHROPIC_API_KEY` のある環境（ローカル）でのみ
> 動作。公開 Vercel ではキーを置かず、`draftMessageAction` が `{ok:false, reason:"no-key"}`
> を返してクライアントがサンプル文（`getMockDraft`）を表示する。無認証の公開URLに
> 課金の入口を作らないため。**よって Upstash 等のレート制限は不採用**（ひとり運用・AIは
> ローカル実データで使う）。将来チーム公開で AI を出すなら、レート制限は middleware では
> 効かないため `draftMessageAction` 冒頭に置く。

```
   ・選択された媒体に応じて文体・長さを調整
       - メール: 件名 + 敬語の本文
       - LINE: 短文・絵文字最小限・親密トーン
       - 電話用トーク台本: 話し言葉・要点リスト
   ・候補者情報・接触ログ直近3件・紹介ネットワークを文脈に
   ・補足フリーテキストの「用件」を必ず反映
   ・過去のやり取り（文面コピー・スクリーンショット画像）が提供された
     場合は、そこから先方の温度感・話題・口調を読み取って反映
   ・押し売りトーンを避け、関係性ベースで自然に
```

### 画像入力（Claude Vision）の仕様

| 項目 | 仕様 |
|------|------|
| 対応モデル | Claude Sonnet 4.6（vision対応）/ Opus 4.7 / Haiku 4.5 もOK |
| 対応形式 | image/jpeg, image/png, image/gif, image/webp |
| 推奨上限 | 1リクエストあたり画像 **3枚まで**（LINE会話履歴3枚あれば文脈十分） |
| サイズ上限 | 各画像 5MB まで（Anthropic API の制約） |
| エンコード | クライアント → Server Action 送信時に base64 化、Anthropic API には `source.type=base64` で渡す |
| トークン消費 | 画像1枚あたり **約1500トークン**（解像度により増減）|
| プライバシー | 候補者の顔写真・個人情報を含む可能性があるため、ユーザーが意図的にアップロードした画像のみ送信。自動取得はしない |

### Prompt Caching でコスト削減

| 区分 | 内容 | キャッシュ |
|------|------|----------|
| system | 文体ガイドライン（数百〜千トークン） | **キャッシュ有効** |
| user | 候補者情報JSON + シーン + 媒体 + 補足 | 毎回変わるためキャッシュなし |

`@anthropic-ai/sdk` の `cache_control: { type: "ephemeral" }` を system に付ける。同じ候補者で複数回生成・再生成するときも、systemはキャッシュ命中（5分窓 / 90%コスト削減）。

### コスト目安（Sonnet 4.6 想定）

| 操作 | 入力トークン | 出力トークン | 概算コスト (USD) |
|------|------------|------------|----------------|
| 初回生成（テキストのみ・system キャッシュなし） | ~1500 | ~500 | $0.012 |
| 再生成（テキストのみ・system キャッシュ命中） | ~1500 | ~500 | $0.005 |
| 微調整生成 | ~1500 | ~500 | $0.005 |
| 初回生成 + 画像1枚 | ~3000 | ~500 | $0.018 |
| 初回生成 + 画像3枚（推奨上限） | ~6000 | ~500 | $0.030 |

月100件生成（うち画像添付20件と想定）= 約 $1.50〜$2.50。Haiku 4.5 ならさらに 1/5 程度（vision性能は若干劣る）。

### 失敗時の挙動

| 失敗パターン | 対応 |
|------------|------|
| Anthropic API がタイムアウト | 10秒待ってリトライ1回、失敗ならエラートースト |
| 認証失敗 (401) | 「ANTHROPIC_API_KEY を確認してください」トースト |
| レート制限 (429) | 「数秒待ってから再試行してください」トースト |
| 不適切コンテンツ判定 | 「生成できませんでした。補足を変えてみてください」トースト |
| 画像サイズ超過 (5MB超) | 「画像が大きすぎます。圧縮してから添付してください」トースト |
| 対応外画像形式 | 「対応形式は JPEG/PNG/GIF/WebP です」トースト |
| 画像枚数超過 (4枚以上) | 「画像は最大3枚までです」トースト + 過剰分を無視 |

### N+1 対策

候補者リスト表示時、各候補者の最終ログを取りに行くと N+1 問題が起きます。
営業候補リストDBに「最終連絡日」プロパティが既にあるので、これを正とすれば追加のクエリは不要です。

```
   悪い例 (N+1):
     営業候補リスト 30件取得 (1 req)
       ↓
     各候補者の最新ログ取得 (30 req)  ← これが破滅
       = 31 req

   良い例 (このプロジェクトの方針):
     営業候補リスト 30件取得 (1 req)
     「最終連絡日」プロパティをそのまま使う
       = 1 req
```

### キャッシュ戦略

| データ | キャッシュ | リバリデート |
|--------|-----------|------------|
| 営業候補リスト一覧 | Server Component で取得、`revalidate: 60` | ステージ変更・候補者追加時に手動 revalidate |
| 候補者詳細 (Pane3) | Pane2 で選択時に取得、選択中だけキャッシュ | 編集確定時に再取得 |
| 接触ログ (Pane4) | 候補者選択時に取得 | ログ追加時に楽観追加 + 数秒後 revalidate |

**Vercel デプロイの落とし穴（解決済み）**: Next 16.2 の Vercel デプロイアダプタ（Adapters API の `onBuildComplete`）が `routes-manifest-deterministic.json` を ENOENT で見失いデプロイ失敗（ビルド自体は毎回成功・ローカルは再現せず）。真因は `next.config.ts` の `outputFileTracingRoot` をサブディレクトリ（`tool`）に固定していたためアダプタの探索パスがずれていたこと。**`outputFileTracingRoot` を削除して解決**（親階層に lockfile が無く元設定は不要だった）。
